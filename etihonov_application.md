**[ НАЗВАНИЕ ПРОЕКТА ]**

“Fathom”

**[ ПРОБЛЕМНОЕ ПОЛЕ ]**
Преподавателям технических и естественно-научных дисциплин (физика, математика, инженерия, программирование) для быстрой проверки знаний на занятиях, кружках или курсах необходим простой и специализированный инструмент. Существующие решения создают непреодолимый барьер:

- Moodle и аналогичные LMS - это как использовать рапиру для операции на виноградинке. Они представляют собой сложные системы управления всем учебным процессом **вуза**. Их развертывание, администрирование и освоение непропорционально сложны для задачи преподавателя-предметника, который хочет просто и быстро создать специализированный тест с формулами и кодом. Также функционалы _курсов, чата и т.п._ просто не нужны.

- Конструкторы тестов (Google Forms, Quizlet) - слишком примитивны. Они не поддерживают необходимый для технических дисциплин контент: математические формулы (LaTeX), фрагменты кода с подсветкой синтаксиса, создание заданий на соответствие или упорядочивание.

Итоговая проблема: Преподаватель, ведущий дополнительное занятие или курс, оказывается в вакууме между _избыточно сложными корпоративными системами_ и _слишком простыми потребительскими сервисами_. В результате он тратит время на преодоление ограничений инструментов, а не на создание качественных заданий.

**[ ЗАКАЗЧИК / ПОТЕНЦИАЛЬНАЯ АУДИТОРИЯ ]**

Основная аудитория: Преподаватель-энтузиаст (в вузе, колледже, на курсах, репетитор), который ведёт занятия по техническим дисциплинам на своём содержании и часто своими силами. Он ценит:

- **Простота и скорость**: возможность развернуть систему за 5 минут на своём ноутбуке или недорогом VPS. Также стоит отметить, что количество библиотек должно быть сокращено. Батарейки не нужны и устанавливать модули не нужно. Пэйволлом не облагается

- **Специализация**: встроенная и бесшовная поддержка LaTeX для формул и подсветки кода «из коробки».

- **Контроль и конфиденциальность**: полный контроль над своими данными (все задания и результаты хранятся в его экосистеме).

Вторичная аудитория:

- Студенты/ученики: для них важна возможность быстро присоединиться к тесту по ссылке без сложной регистрации и получить ясную обратную связь.

- Методисты и авторы: заинтересованы в открытом формате хранения заданий, который позволяет вести версионность (например, через Git) и делиться банками вопросов и тестами.

**[ АППАРАТНЫЕ / ПРОГРАММНЫЕ ТРЕБОВАНИЯ ]**

Продукт разрабатывается как кроссплатформенное веб-приложение, развертываемое одним из двух способов:

1. Минимальный (основной сценарий): Запуск на ноутбуке или ПК преподавателя для проведения занятий в классе или онлайн. Работает в локальной сети.
   - Клиент: Любой современный браузер (Chrome, Firefox, Edge последних версий).

   - Сервер: Docker Desktop или прямой запуск бинарного файла (для Windows/macOS/Linux). Минимальные требования: 1 CPU, 1 ГБ ОЗУ, 10 ГБ на диске.

2. Макс: Развертывание на публичном сервере(VDS) для постоянного доступа.
   - Сервер: Любой VDS с ОС Linux (Ubuntu 22.04 LTS или аналоги) и Docker. Минимальная конфигурация: 2 CPU, 2 ГБ ОЗУ, 10 ГБ SSD. Добавлены сис. требования postgres:16-alpine

**[ ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ ]**

1. Для преподавателя (создание и запуск):
   - Редактор из коробки: Единое поле ввода для условия вопроса с мгновенным предпросмотром. Поддержка смешанного контента: обычный текст, Markdown(для форматирования, GFM), LaTeX(формулы отображаются рядом), код(с автоматической подсветкой для популярных ЯП).

   - Типы вопросов, необходимые для технических предметов:
     - Один/несколько правильных ответов.

     - Свободный ответ (с проверкой по шаблону/регулярному выражению).

     - Установление соответствия.

     - Упорядочивание последовательности.

     - Точный ответ (просто ввод).

   - Работа с заданиями: Создание банка заданий, объединение в тесты/контесты.

   - Запуск теста: Получение короткой ссылки и QR-кода для доступа учеников. Настройка времени, количества попыток.

   - Анализ на лету: Мгновенное получение результатов после завершения теста: таблица ответов, статистика по вопросам, возможность выгрузки в CSV.

   - Импорт/экспорт в/из .md(для теста) и бандл из .yaml(инфо о тесте) + .md(задания)

1. Для студента (прохождение):
   - Доступ по ссылке или QR-коду.

   - Чистый, адаптивный интерфейс для прохождения теста.

   - Автосохранение ответов.

   - Просмотр результата (если разрешил преподаватель): свои ответы и правильные.

**[ ПОХОЖИЕ / АНАЛОГИЧНЫЕ ПРОДУКТЫ ]**

1. Moodle Quiz: Институциональная LMS для управления учебным процессом всего вуза. Чрезвычайно сложен в развертывании(конечно, если не использовать docker), администрировании и ежедневном использовании для создания одного теста. Некоторые функции требуют отдельной настройки.
2. Google/Microsoft Forms: Универсальный облачный конструктор опросов. Не поддерживают LaTeX и код. Нет полного и прозрачного контроля над данными (они в облаке).
3. Stepik: Платформа для создания публичных курсов, особенно с уклоном в программирование. Ориентирован на публикацию курсов для широкой аудитории, менее удобен для приватного, быстрого тестирования своей группы.
4. iSpring Suite: Проприетарный авторский инструмент для корпоративного e-learning. Закрытый, платный, нельзя развернуть у себя.

Ключевое отличие: Этот проект - персональный open-source инструмент, который не пытается быть большой и хорошей во всём LMS, а решает одну задачу идеально: дать преподавателю-предметнику максимально простой и мощный способ создать и провести специализированный тест, сохранив полный контроль над данными и процессом.

**[ ИНСТРУМЕНТЫ РАЗРАБОТКИ, ИНФОРМАЦИЯ О БД ]**

- Бэкенд: Golang + Chi + Bun.

- Фронтенд: Svelte + TypeScript + Vite. Формулы: KaTeX. Редактор кода: CodeMirror.

- БД: SQLite или PostgreSQL на выбор.

- Развертывание: Docker Compose как основной способ; предоставление бинарных файлов для основных ОС.

**[ ВОЗМОЖНЫЕ РИСКИ ]**

- Сложность создания интуитивного гибридного редактора - смягчается использованием проверенных библиотек (CodeMirror, KaTeX, Bun) и фокусом на MVP.

- Попытка сделать «ещё один Moodle» - главный управленческий риск. Смягчение: жёсткое следование сформулированной философии «инструмент для преподавателя, а не система для организации».

- Недооценка необходимой простоты развертывания - смягчается фокусом на Docker и SQLite с первого этапа.

- Как заметил эксперт про SQLite: "очень много проблем начиная от поточки и заканчивая целостностью данных." - использовать уровень БД как БД, а не как генератор uuid для целостности, а проблем с многопоточностью не возникнет, если в архитектуре можно запустить только 1 тест за время и он полностью кэшируется

**[ СТОИТ ЗАМЕТИТЬ ]**

- БД здесь не "центр правды", а регистр. Вся основная информация идет от папок. Этот подход упрощает импорт/экспорт и контроль в системах контроля версий.
- Запускать можно ТОЛЬКО 1 тест за раз. Для полного контроля, а так же проект задумывался как тот, который можно запустить на картошке с лимоном.
- Выбор между sqlite и postgres дается по той же причине, но нагрузка на них(как сказано выше) не большая.
- В _критериях не сказано_, что за кнопка **Помощь**, поэтому моя кнопка будет вести на github pages документацией(Форматированный и plaintext для ИИ ассистентов).
- Будет(уже разработан) инструмент для настройки Fathom не запуская его. Установка по желанию. Для установки нужен бинарник go. \
  Возможности:
  - Умная настройка конфигурации приложения
  - Регистрация тестов/вопросов в оффлайне
  - Регистрация учеников
  - Пропуск настройки через GUI(будет описано в документации)
  - Регенерация приложения

**[ СМЕНА ТЕХНОЛОГИЙ ]**

- Gin на chi: \
  gin - мощный фрэймворк для сильной нагрузке на сервер, имеет кастомный путь задания middleware(лучше, чем net/http) и такие вещи как JSON расшифровщик
  chi - буквально легковесная обертка на net/http для упрощенного задания путей, по скорости и легкости библиотеки лучше.
  Итог: chi подходит лучше по философии проекта
- React на Svelte: \
  **React** - _библиотека_, которая создает виртуальный DOM и большой размер бандла. \
  Из плюсов:
  - Он простой(в изучении)
  - Его знают все
  - "Взрослая" система библиотек

  Из минусов:
  - _Он тяжелый_(в рантайме)
  - Он использует структуры, присущие фрэймворку(хуки не по регистрации, а по названию)

  **Svelte** - _библиотека_(не путать со SvelteKit, это фрэймворк построенный на svelte). Компилируется в _чистый js_, без рантайма и domа. \
  Из плюсов:
  - Он очень простой
  - Он очень легкий
  - Он очень быстрый(буквально макс. доступная скорость из-за компиляции)

  Из минусов:
  - Количество библиотек меньше

  Так как приложению не нужно много библиотек, то svelte становится натуральным выбором
